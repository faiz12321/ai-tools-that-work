git: fatal: cannot lock ref 'refs/heads/feature/api' - why can't I create my branch?

Short answer

A branch named feature already exists, so feature/api is physically impossible: git stores every ref as a file under .git/refs/heads/, and one path cannot be both a file (feature) and a folder (feature/api). Fix it by moving the blocker with git - git branch -m feature feature-old, or git branch -d feature if it is merged - then create the branch. Never delete files under .git by hand. The rule is symmetric and applies to tags and remote branches too.

Common mistakes with 'cannot lock ref'

  1. Deleting .git/refs/heads/feature by hand. Refs can also live in .git/packed-refs, per-worktree ref dirs, and reflogs. Hand-deleting the loose file leaves those stale and can corrupt later operations. git branch -m and git branch -d update every location at once.
  2. Thinking the two names are independent. feature and feature/api are not separate strings to the filesystem - one is a prefix of the other, and a path cannot be both a file and a folder.
  3. Confusing it with a stale lockfile. 'Unable to create ... .lock: File exists' means an interrupted process left a lock - remove the .lock after checking no git is running. 'exists; cannot create' is structural; no lockfile cleanup fixes it.
  4. Forgetting the rule covers tags and remotes. refs/tags/release blocks refs/tags/release/notes, and pushing a colliding name hits the same refusal from the remote. Pick one naming convention per namespace.

Frequently asked questions

What does 'exists; cannot create' actually mean?

A ref already occupies part of the path you are creating. Branch feature exists as a file; feature/api needs feature to be a folder. The filesystem forbids both, so git refuses before changing anything - nothing is locked by another process.

How do I fix it?

Move the blocker with git: git branch -m feature feature-old to rename it (commit and reflog come along), or git branch -d feature to delete it once merged. Then git switch -c feature/api works. The reverse collision (creating feature while feature/api exists) is fixed the same way.

Can I just delete the file under .git/refs/heads?

No. Loose ref files are only one place a name is recorded: packed-refs, per-worktree refs and reflogs also track it. Deleting the file by hand desynchronises them and can break checkouts and gc. Always rename or delete through git itself.

Is this the same as 'Unable to create ... .lock: File exists'?

No - that is a stale lockfile from an interrupted git process, fixed by removing the named .lock file once you confirm no git is running. The exists; cannot create wording means a structural ref collision and has nothing to do with lockfiles.

Does this apply to tags and remote branches?

Yes. Every ref namespace follows the one-path rule: tag release blocks tag release/notes, and a push that would create a colliding remote ref fails with the same message. Mixed naming conventions are the usual cause.
