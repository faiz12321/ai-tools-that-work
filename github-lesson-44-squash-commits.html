git: squash your last N commits into one (rebase -i)

Short answer

git rebase -i HEAD~N opens a todo list of your last N commits: keep the first as pick, change the rest to squash, save, then edit the combined message. Git builds ONE new commit with all the changes and re-points your branch at it. Nothing is deleted - the old commits sit in the reflog for weeks. Squash is a pre-publish tool: safe while the branch is yours, a rewrite others must agree to once it is pushed and pulled.

Common mistakes with squashing

  1. Squashing pushed commits. A squash creates new hashes, so your branch and every pulled copy diverge. Force-pushing the rewrite strands teammates. Squash before publishing, or coordinate the rewrite with the whole team.
  2. Rebasing with a dirty tree. Uncommitted changes block the rebase - or worse, get swept into the wrong commit. git status first; stash or commit drafts before rewriting.
  3. Squashing the FIRST commit. In the todo list the first line must stay pick - there is nothing above it to fold into. Changing it to squash is the classic 'cannot squash without a previous commit' error.
  4. Fearing the rewrite. A local squash is recoverable for weeks: the old tip hash sits in git reflog, and git reset --hard restores it. The dangerous squash is not the local one - it is the pushed one.

Frequently asked questions

How do I squash my last N commits together?

Run git rebase -i HEAD~N. In the todo list, keep the first commit as pick and change the rest to squash (or s). Save, then edit the combined commit message. Git builds ONE new commit containing all the changes and re-points your branch at it. The old commits become unreachable but stay in the reflog for weeks.

Does squashing delete my old commits?

No. The branch pointer moves to the new combined commit; the originals become unreachable but remain in the object store and the reflog for weeks by default. If the squash went wrong, find the old tip in git reflog and git reset --hard to it.

Can I squash commits I already pushed?

Only with coordination. Squashing rewrites history: the new commit has a new hash, so your branch and everyone else's diverge. If others pulled the old commits, a force push strands their work. Squash freely while the branch is yours alone; once shared, either add new commits or agree on the rewrite as a team and use --force-with-lease.

What is the difference between squash and fixup in git rebase -i?

Squash combines the changes AND the commit messages (you edit the combined message). Fixup combines the changes but DISCARDS the folded commits' messages, keeping only the first one. Use fixup for typo and oops commits whose messages say nothing.

What does HEAD~4 mean in git rebase -i HEAD~4?

HEAD~4 names the commit four steps before your tip - the rebase rewrites everything AFTER it, which is exactly your last four commits. The first listed commit stays as pick; the rest get folded into it.
