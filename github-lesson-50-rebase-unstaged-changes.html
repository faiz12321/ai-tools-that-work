git: "cannot rebase: You have unstaged changes" - how do I fix it?

Short answer

Rebase rewrites your working tree, so it demands a clean one - this is protection, not failure. Park the edits: git stash push -m label, run git rebase main, then git stash pop to land them on the new base. If the work is coherent, committing it satisfies the guard too. Note that staged changes trigger a second refusal (Your index contains uncommitted changes) - staged is not committed. git rebase --autostash automates the whole dance.

Common mistakes with the rebase guard

  1. Thinking staged means safe. git add moves edits to the index, and rebase refuses that too ('Your index contains uncommitted changes') - the index is rebase's construction zone. Commit or stash; only those two states pass.
  2. git checkout -- . to make it go away. Discarding the edits 'fixes' the guard by destroying the work. If you catch yourself reaching for a destructive shortcut, stop - stash is one command and fully recoverable.
  3. Popping and forgetting. A failed pop KEEPS the stash entry (that is the safety design), but people resolve the conflict, move on, and leave stale entries for months. git stash list after any pop; drop what you truly merged.
  4. Rebasing pushed branches casually. Rebase rewrites hashes (watch the login-form commit change hash in this recording). On a branch others have pulled, that is a force-push-class event - coordinate, and push with --force-with-lease only.

Frequently asked questions

What does 'cannot rebase: You have unstaged changes' mean?

A rebase moves HEAD and replays your commits, rewriting the working tree - it refuses to run over uncommitted edits because it cannot tell which snapshot they belong to. Make the edits safe first: commit or stash.

How do I fix it?

git stash push -m label, then git rebase main, then git stash pop. If the edits are coherent, git commit them instead - a committed tree also passes. git rebase --autostash does the stash dance automatically.

Why does git rebase still refuse after git add?

Staged is not committed - the second error is 'Your index contains uncommitted changes'. The index is where the rebase builds each replayed commit, so it must be clean too. Commit or stash the staged changes.

Is git stash pop safe after a rebase? What if it conflicts?

Yes - stashed edits are real commits. pop restores them onto the new base and drops the entry; on conflict it STOPS and KEEPS the entry, so nothing is lost. Resolve, then drop the entry yourself.

What does git rebase --autostash do?

stash push + rebase + stash pop in one command. Best when your dirty files are unrelated to the replayed commits; a conflicting auto-pop behaves like any stash conflict with the entry kept. Default it via git config --global rebase.autoStash true.
