git: CONFLICT (modify/delete) - one branch edited a file the other deleted. How do I resolve it?

Short answer

The conflict is about the file's existence, not its lines - so there are no <<<<<<< markers. git leaves the modified version in your tree and waits for a verdict: git add api.py to keep the edited file, or git rm api.py to accept the deletion. Either way, finish with git commit. Read git ls-files -u first: stage 1 + stage 3 with no stage 2 is the modify/delete signature. And review the surviving content before choosing - an edit on a file you meant to retire may need porting to its replacement.

Common mistakes with modify/delete conflicts

  1. Looking for conflict markers inside the file. There are none - one side has no file to compare. The conflict lives in the index (git ls-files -u), not in the file's contents. cat shows the surviving version, clean.
  2. Resolving with checkout --ours / --theirs. Those pick content for line-level conflicts. Here --ours has no file to restore (we deleted it) and --theirs merely re-extracts what is already in the tree. The existence question is answered at the index level: git add or git rm.
  3. Running git rm without reading the other side's edit. The deletion wins, and the rate limiting (or whatever the edit was) is gone from the working tree. It still exists in the other branch's commit, but 'it is in history somewhere' is not a plan - review and port first.
  4. Assuming merge --continue resolves it. It concludes a RESOLVED merge only. With unmerged paths it refuses: 'Committing is not possible because you have unmerged files.' The verdict (add or rm) always comes first.

Frequently asked questions

What does CONFLICT (modify/delete) mean?

One branch deleted the file while the other modified it. git cannot choose between 'gone' and 'changed', so it parks the question: the modified version sits in your tree, unmerged entries sit in the index, and the merge waits for git add (keep) or git rm (delete).

How do I resolve it and keep the file?

git add path, then git commit. Status will show 'new file: path' - from your branch's view the file was deleted, so keeping it registers as new. The staged content is the other branch's version, building on the full history of the path.

How do I resolve it by deleting the file?

git rm path, then git commit - but review first: cat the file git left in your tree and port any edit that still matters to the replacement file. The other branch's commit remains reachable in history either way.

What do the ls-files -u stage numbers mean here?

Stage 1 = common ancestor's version, stage 3 = their modified version, and stage 2 (ours) is MISSING because our side deleted the file - there is no blob to reference. Content conflicts show all three; the gap is the modify/delete signature.

What does 'deleted by us' mean - and why does it flip?

US is the branch you are on, THEM the one being merged. 'deleted by us: api.py' means your branch deleted it. On the other branch the same merge reads 'deleted by them'. The status advice 'use git add/rm as appropriate' is your menu: add keeps, rm deletes.
