git: "untracked working tree files would be overwritten by merge" - how do I fix it?

Short answer

git will not overwrite an untracked file - its only copy is your disk, so the merge aborts and asks you to decide. Look at what is coming first: git show origin/main:path. Keep your draft by renaming it aside: mv path path.local, then git pull again. Remove confirmed junk with git clean -n path (dry run) then git clean -f path. Unsure? git stash -u, pull, git stash pop. There is no pull flag that skips this - the decision is the point.

Common mistakes with untracked collisions

  1. Running git clean -f without the dry run. The -n rehearsal is the only review you get: untracked files have no undo. Read the 'Would remove' list every time, scope clean to a path, and never reflexively add -x (it also deletes ignored files like .env and build caches).
  2. Staging the untracked file to 'fix' it. git add does not merge anything - it upgrades the collision from untracked to a staged local change, and the pull now fails with a different error. Move, remove, or stash; do not add.
  3. Assuming reset --hard cleans everything. reset --hard rewrites TRACKED files only; untracked collisions survive it. People run it, feel safe, and hit the same abort on the next pull.
  4. Deleting the incoming file's future without looking. Removing your untracked file before reading git show origin/main:path can mean losing the only copy of a real config. Look first; the teammate's version is already fetched and printable.

Frequently asked questions

What does 'untracked working tree files would be overwritten by merge' mean?

The incoming commit contains tracked files at paths where you have untracked files. git refuses to overwrite an untracked file because its only copy is on your disk - nothing in history could restore it. The merge aborts; nothing is lost.

How do I fix it?

Per file: keep a draft by renaming it aside (mv path path.local) and pull again; remove confirmed junk with git clean -n path then git clean -f path; if unsure, git stash -u, pull, then git stash pop - the files stay recoverable in the stash entry.

Does git pull --force or reset --hard overwrite untracked files?

No. git pull has no force flag for this, and git reset --hard rewrites only tracked files - untracked ones survive even that. Only git clean (permanently) and git stash -u (recoverably) remove untracked files.

Is git clean dangerous? How do I use it safely?

It permanently deletes untracked files - no undo. Always run git clean -n first and read the list, scope it to a path (git clean -f logs/), and avoid -x unless you also mean to delete ignored files.

How do I see the incoming file that collides with mine?

The failed pull already fetched it: git show origin/main:path/to/file prints the tracked version from the remote branch. Compare, then decide - keep yours aside, discard yours, or reconcile both after the pull.
