git: committed to the wrong branch? Move the commits

Short answer

Branches are movable pointers, and a commit is safe while ANY pointer holds it. So: git branch feature first (a second pointer on the tip), then git reset --hard HEAD~2 (main lets go), then git switch feature and keep working. The commits keep their hashes - nothing is rewritten or deleted. This is safe only while the branch is local; if you already pushed, use git revert or coordinate instead.

Common mistakes with misplaced commits

  1. Resetting before branching. git reset --hard moves only the current branch. If nothing else holds the tip, the commits drop to reflog-only reachability - recoverable, but a rescue. git branch feature first makes the reset risk-free.
  2. Reaching for rebase or cherry-pick. Both create NEW commits with new hashes. Here the commits are perfect; only the pointers are wrong. Moving pointers keeps the hashes, the timestamps, and your sanity.
  3. Copying the fix to a pushed branch. The branch-first reset is a LOCAL fix. Once others have the commits, moving main backward strands them. On shared history the fix is git revert (additive undo) or a coordinated reset with --force-with-lease.
  4. Panicking because the commits "disappeared". After the reset, the discount commits vanish from main's log - but they are exactly where feature points, hashes unchanged. git log --all --decorate shows every pointer at once when in doubt.

Frequently asked questions

I committed to the wrong branch. How do I move the last commits to a new branch?

Three moves, in this order: git branch feature (put a second pointer on the current tip so the commits stay referenced), git reset --hard HEAD~N (move the current branch back N commits), git switch feature (continue the work there). The commits keep their hashes - you moved pointers, not commits.

Why must I create the new branch before running git reset --hard?

reset --hard moves only the branch you are on. If main is the only pointer holding the new commits, resetting it makes them unreachable except through the reflog - a rescue, not a plan. Creating the feature branch first means the commits are held twice when main lets go, so the reset is risk-free.

Does git reset --hard HEAD~2 delete my commits?

No. It moves the current branch pointer back two commits and resets the working tree to match. The two commits still exist in the object store; as long as another branch or tag points at them they are fully alive. Even with no pointer at all, they linger in the reflog for weeks before garbage collection.

What if I already pushed the branch with the misplaced commits?

Do not reset it. Moving a branch backward after others have pulled rewrites shared history and strands their work. Use git revert to add undoing commits, or coordinate with the team before any reset and force-with-lease push. The local branch-first reset fix is safe only while the branch is yours alone.

Can I move the commits without git switch?

Yes - the order can vary: you can git switch -c feature first, then move main back with git branch -f main HEAD~2, or use git checkout -b plus the same reset. What does not vary is the safety rule: some reference must hold the commits before the original branch lets go.
