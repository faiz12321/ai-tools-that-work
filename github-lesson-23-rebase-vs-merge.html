git: rebase vs merge - which one and when?

Short answer

git merge feature joins the branches with a merge commit and preserves the true split-and-join shape of history. git rebase main (from your feature branch) replays your commits on top of main as new commits, so history reads as one straight line. Merge is always safe; rebase only for commits nobody else has pulled.

Common mistakes with rebase and merge

  1. Rebasing shared commits. Rebase gives every replayed commit a new hash. If a teammate has the old ones, your "tidy" history now conflicts with theirs. Only rebase commits that never left your machine.
  2. Expecting rebase to keep the same hashes. A hash covers the parent too, so a new parent means a new commit. Same change, different commit - as the recording shows (362b4f3 became 4cc63ba).
  3. Thinking merge loses information. The opposite: the merge commit records that two lines of work were joined and by whom. Rebase is what erases that shape, on purpose.
  4. Rebasing through conflicts blindly. Rebase replays commit by commit and can stop at each one. For a long branch, that can mean resolving the same conflict several times; merging resolves once.

Frequently asked questions

When do you use git rebase instead of git merge?

Use merge when you want to preserve the true shape of history - a merge commit records that two lines of work were joined. Use rebase to tidy your own unpushed commits: it replays them onto the latest main so history reads as a straight line.

What is the golden rule of git rebase?

Never rebase commits that exist outside your repository - commits someone else may have pulled. Rebase rewrites them into new commits with new hashes, so their copies and yours diverge.

Does rebase delete my commits?

It creates new commits with the same changes and new hashes, and moves your branch to them. The originals stay reachable through the reflog for a while, so a mistaken rebase is usually recoverable - but treat rebase as rewriting history.

Which is safer for a shared branch?

Merge. A merge adds one new commit and moves no existing history, so it is always safe on shared branches. Rebase rewrites existing commits, which is only safe for commits nobody else has.

Why does a rebased commit have a different hash?

A commit's hash covers its parent, tree, author, message and dates. Rebase gives the commit a new parent (the tip of the branch you rebased onto), so the hash must change even though the code change is the same.
