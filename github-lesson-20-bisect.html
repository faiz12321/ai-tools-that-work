git: which commit broke it? (git bisect)

Short answer

git bisect start HEAD <known-good-hash>, then either answer git bisect good/bad at each checkout, or hand git a test: git bisect run ./check.sh. git halves the suspects each round and names the exact first bad commit. Finish with git bisect reset.

Common mistakes with bisect

  1. Starting with a dirty tree. Bisect checks out other commits; uncommitted edits either block it or travel along and corrupt every test. Commit, stash, or discard first.
  2. Marking the endpoints wrong. 'bad' must be a commit where the bug EXISTS (usually HEAD), 'good' one where it does not. Swapping them makes git hunt confidently in the wrong direction.
  3. A flaky test script. If check.sh sometimes exits 1 on good code, bisect walks to the wrong answer with total confidence. Make the test deterministic before you run it.
  4. Forgetting git bisect reset. The search ends on a detached HEAD at some old commit. reset takes you back to your branch; skipping it is how people 'lose' work (lesson 17's reflog would find it).

Frequently asked questions

How do I find which commit introduced a bug?

Run git bisect start HEAD <known-good-hash>, then answer 'good' or 'bad' at each step - or hand git a test script with git bisect run ./check.sh. git binary-searches and names the first bad commit, usually in a handful of tests.

What does a bisect test script need to do?

Exit 0 when the code at the current commit is good, exit 1 (or any non-zero except 125) when it is bad. Exit 125 means 'cannot test this commit' and git skips it.

Why is bisect faster than checking commits one by one?

Binary search halves the suspects each test. 100 commits need about 7 tests; 1000 need about 10. Reading every commit linearly costs one test per commit.

Does bisect change my files?

It checks out the middle commits as it searches, so your working tree moves around. git bisect reset returns you to your branch when you are done. Start with a clean tree.

What if I cannot tell good from bad on some commit?

Run git bisect skip and git picks a nearby commit instead. In a script, exit code 125 does the same thing automatically.

Do 'good' and 'bad' have to mean old and new?

By default bad is the newer broken state and good is the older working one. You can swap the words with --term-old and --term-new when searching for the commit that FIXED something.
