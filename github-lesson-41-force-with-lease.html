git: push --force vs --force-with-lease (what "stale info" means)

Short answer

git push --force overwrites the remote branch with your local history unconditionally - a teammate's commit you have never seen falls off silently. git push --force-with-lease adds a contract: overwrite ONLY if the remote is still exactly where your remote-tracking bookmark says. If someone pushed since your last fetch, it refuses with ! [rejected] (stale info). Use the lease spelling always - and after every fetch, look at what came in, because once your bookmark updates, the lease trusts it.

Common mistakes with force pushing

  1. Reaching for plain --force. It overwrites the remote pointer unconditionally. --force-with-lease costs one extra word and refuses exactly when it matters: when the remote moved since your last fetch.
  2. Trusting the lease after a fetch. The lease compares the remote to your bookmark. Fetch updates the bookmark - so a force right after a fetch succeeds even over a teammate's minutes-old commit. The lease covers unseen work; seen work is on you.
  3. Following the 'pull first' hint after a rewrite. After amend or rebase, pulling merges the OLD commit back next to your new one - the exact history you just removed. Reject the hint; the right question is what to overwrite, and how safely.
  4. Rewriting shared branches. Amend and rebase are for branches you own. On main or a release branch, rewriting pushed history forces every teammate to repair their clones. Use git revert there instead.

Frequently asked questions

What is the difference between git push --force and --force-with-lease?

--force overwrites the remote branch with your local history unconditionally. --force-with-lease adds a contract: it overwrites ONLY if the remote branch is still exactly where your remote-tracking bookmark says it is. If someone pushed since your last fetch, the lease check fails with '(stale info)' and the push is refused - protecting work you have never seen.

What does "rejected - stale info" mean on git push --force-with-lease?

The remote branch has moved since your remote-tracking bookmark was last updated - someone (or another machine of yours) pushed commits you have not fetched. Git refuses to overwrite them. Run git fetch origin, look at what came in, integrate or coordinate, then force-with-lease again if overwriting is still right.

Does --force-with-lease make force-pushing safe?

Safer, not safe. The lease trusts your remote-tracking bookmark: after you fetch, the bookmark matches the remote, so the check passes and the force succeeds - even if it overwrites a teammate's fresh commit. The lease protects you from work you have not seen; reviewing what each fetch brings in protects the rest. Never use plain --force.

Why was my push rejected as non-fast-forward after git commit --amend?

Amending rewrites the commit into a NEW hash, so your branch no longer contains the commit the remote has - the two histories diverged. A normal push only adds commits; replacing history requires an explicit force, and the safe spelling is git push --force-with-lease.

When is it OK to force push?

On a branch you own (a feature branch under review, your solo work), with --force-with-lease, after checking what the last fetch brought in. On shared branches like main, rewriting pushed history is usually the wrong move entirely - prefer git revert, which adds a new commit instead of replacing old ones.
