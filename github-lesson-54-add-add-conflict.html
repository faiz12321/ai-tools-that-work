git: CONFLICT (add/add) - two branches created the same file. How do I resolve it?

Short answer

Both branches created deploy.sh independently, so git cannot pick between two creations - it marks both versions inside the file with <<<<<<< / ======= / >>>>>>>. Edit the file into the version you want (one side, or a hand-written combination), then git add deploy.sh and git commit. If one side should win wholesale: git checkout --ours or --theirs, then add and commit. The tell in git ls-files -u: stages 2 and 3, with no stage 1 - the file never existed in the common ancestor.

Resolving means rewriting the conflicted file - both originals stay safe in their commits, so a bad resolution is always recoverable (git merge --abort before committing; the branch hashes after). Never commit a file that still contains conflict-marker lines.

Common mistakes with add/add conflicts

  1. Committing with markers still in the file. <<<<<<< and >>>>>>> lines are valid text to git - nothing stops the commit. Always re-read the resolved file (or grep for '^<<<<<<<') before git add.
  2. Assuming checkout --theirs is required. It is only right when one creation should win wholesale (substitutes, not complements). When both creations carry something the final file needs - staging AND production targets here - hand-merge.
  3. Reading the missing stage wrong in ls-files -u. No stage 1 means 'not in the ancestor' (add/add); no stage 2 means 'we deleted it' (modify/delete); no stage 3 means 'they deleted it'. The gap IS the diagnosis.
  4. Deleting one branch's file to 'resolve' it. git rm drops the path entirely - that answers a modify/delete question nobody asked. Add/add asks what the file should contain, not whether it should exist.

Frequently asked questions

What does CONFLICT (add/add) mean?

Both branches created the same path with different content and no common ancestor version to compare against. git leaves both versions inside the file between conflict markers and waits for your edit plus git add.

How do I resolve it?

Edit the file into the final version - by hand, or git checkout --ours/--theirs <file> for a wholesale pick - then git add <file> and git commit. Status moves from 'both added' to 'All conflicts fixed but you are still merging' to a clean merge commit.

Why is there no stage 1 in git ls-files -u?

Stage 1 is the ancestor version, and the file did not exist in the common ancestor - you see only stage 2 (ours) and stage 3 (theirs). Missing stage 2 instead would mean your side deleted the file (modify/delete).

Will the losing version be lost?

No. Both original creations remain in their branch commits forever, reachable by hash. Your resolution adds a new version on top; it never rewrites the two parents. (That is why the cleanup prints 'was <hash>' - those hashes are recovery anchors.)

How do I avoid add/add conflicts?

Coordinate who creates new shared paths (one branch scaffolds, others branch after it lands), and consider a .gitattributes merge driver such as union for files where combining lines is always correct. git rerere replays past resolutions but does not prevent first-time conflicts.
