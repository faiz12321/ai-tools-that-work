git: fatal: refusing to merge unrelated histories. How do I fix it?

Short answer

The two branches share no commit at all: they are separate projects. If they genuinely belong together, run git merge branch-name --allow-unrelated-histories. If you do not recognize the other history, stop; joining mixes its whole past into yours and undoing that means rewriting history.

Safety: --allow-unrelated-histories permanently joins two projects' pasts. Use it only when you know both histories and want them merged. Never use it to silence the refusal on an unfamiliar history; walking away is the correct fix there.

Common mistakes with unrelated histories

  1. Adding --allow-unrelated-histories without reading the situation. The flag is not a fix-all; it is a declaration that two projects belong together. If one is a stranger, you have just merged a stranger's past into yours.
  2. Re-cloning or reinitializing to escape. git init over an existing clone or pulling into a fresh repo is how many people meet this error. The histories are unrelated because one of them was restarted.
  3. Expecting conflicts that never come. With no shared base, only files present on both sides can conflict; the rest simply arrive. In this recording the merge added books.txt cleanly.
  4. Trying --force. There is nothing to force; the refusal is a policy question, not a conflict. Force flags do not answer it.
  5. Panicking about data loss. The refusal changes nothing. Both branches sit untouched until you deliberately join them.

Frequently asked questions

What are unrelated histories?

Two lines of commits that share no common ancestor. Each started from its own first commit, so git has no shared base to merge from.

Why does git refuse to merge them?

Because joining two separate projects is almost always an accident, like pulling from the wrong repository. git refuses by default so you stop and check.

What is the fix?

When you are sure the two histories belong together, run git merge branch-name --allow-unrelated-histories. git then merges them as if they shared an empty base.

When should I NOT allow it?

When the other history is a stranger: a wrong remote, a mistyped URL, a project you do not recognize. Joining mixes its whole past into yours, and undoing that means rewriting history.

Will my files conflict?

Files that exist on both sides with different content conflict, exactly like a normal merge; you resolve them the same way. Files that exist on only one side come across cleanly.

Does this come up outside merges?

Yes, most often on git pull from a fresh remote or after reinitializing a repository that already had a remote. The meaning and the fix are the same.
