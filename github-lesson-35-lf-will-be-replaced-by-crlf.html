git: "warning: LF will be replaced by CRLF" - what it means and what to do

Short answer

Nothing broke. Git is warning that your file has LF (Unix) line endings and that, with core.autocrlf=true (the usual Windows setup), it will check the file out with CRLF endings later. The add already succeeded - git status proves it. The lasting fix is not silencing the warning but committing one line: * text=auto in .gitattributes, so the rule travels with the repo.

Common mistakes with the LF/CRLF warning

  1. Reading the warning as a failed add. Warnings never block staging. git status shows the files as added on the first try - re-running or reaching for --force fixes nothing because nothing is broken.
  2. Silencing it with core.autocrlf=false. That hides the notice but keeps the mixed endings that caused it. The next teammate's checkout still flips between LF and CRLF and every diff drowns in whole-file noise.
  3. Fixing endings file by file. Hand-converting files one at a time does not scale and does not survive the next clone. One .gitattributes line (* text=auto) plus git add --renormalize . settles the whole repo.
  4. Copying a Windows config onto a Mac/Linux machine. Machine settings are per-person and per-laptop, and they disagree with each other. The rule belongs in the repository, where every clone gets it automatically.

Frequently asked questions

What does "warning: LF will be replaced by CRLF" mean?

Your file uses LF (Unix) line endings. With core.autocrlf=true, common on Windows, git converts LF to CRLF when it checks files out into your working tree, and converts CRLF back to LF when you commit. The warning is advance notice of that checkout-time conversion - the add itself succeeded.

Is the LF/CRLF warning an error? Did my git add fail?

No. A warning is not an error. git add staged the files normally; run git status and you will see them as added. Nothing needs re-running, and there is no --force involved.

What is the difference between LF and CRLF?

Two ways to mark a line ending: LF (one byte, Unix, Mac and Linux) and CRLF (two bytes, the Windows tradition). Editors and compilers handle both, but mixed endings in one repo produce noisy diffs where every line looks changed.

Should I use core.autocrlf true, input, or false?

true converts to CRLF in your working tree (typical on Windows); input converts to LF on commit only, leaving checkouts alone (typical on Mac/Linux); false disables conversion. Better than any of these: a committed .gitattributes with * text=auto, because the rule travels with the repo instead of living on each machine.

How do I stop the warning for good?

Commit a .gitattributes file containing * text=auto. Git then manages endings by the repo's own rule on every clone: LF in history, native endings in each working tree. For existing mixed files, git add --renormalize . rewrites them to match.
