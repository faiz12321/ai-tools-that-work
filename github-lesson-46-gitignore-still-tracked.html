git: it is in .gitignore but git still tracks it. How do I fix it?

Short answer

Ignore rules only gate UNTRACKED files - once a file is committed, .gitignore stops applying to it. Untrack it with git rm --cached <file>: the file leaves git's index but stays on your disk. Commit that removal together with the .gitignore, and git forgets the file going forward. Two warnings: teammates who pull the commit lose THEIR working-tree copy of the file, and past commits still contain it - rotate any real secret.

Common mistakes with tracked-but-ignored files

  1. Editing .gitignore and waiting for git to forget. Ignore rules never apply to tracked files - not after a commit of .gitignore, not after a pull, not ever. The only way out is untracking: git rm --cached, then commit.
  2. Using plain git rm and losing the local file. Without --cached, the file is deleted from disk too. For config files your app still needs locally, that is an instant breakage. --cached is the flag that means 'git, let go - but leave my copy alone'.
  3. Forgetting the team. The commit you push records a deletion. Teammates pulling it into a clean tree lose their working-tree copy of config.env. Send the warning first: copy the file aside, then pull.
  4. Thinking untracking unpublishes a secret. History still contains every past version. If a real key or password was committed, rotate it immediately - and if history must be cleaned, that is a filter-repo rewrite with team coordination, not a --cached.

Frequently asked questions

Why does git still track a file that is in .gitignore?

Ignore rules only answer 'should git notice this UNTRACKED file?' Once a file is committed it is tracked, and tracked files are exempt from .gitignore completely - that is why git check-ignore prints nothing for them unless you pass --no-index. Untrack with git rm --cached <file>, then commit the removal with the .gitignore.

How do I make git forget a tracked file but keep it on disk?

Run git rm --cached <file> - it removes the file from the index only, leaving the working-tree file alone. Add it to .gitignore and commit both together: the commit stops tracking going forward, the rule blocks accidental re-adding.

Does git rm --cached delete the file for teammates when they pull?

Yes. The commit records a deletion, and a pull applies it to every clean tracked copy. Uncommitted changes block the pull instead; the file remains recoverable from history. Warn the team to copy it aside first.

Does git rm --cached remove the file from history?

No. Past commits still contain it - git log -- <file> shows where it lived. History removal needs a rewrite tool (git filter-repo) and team coordination. If the file held a real secret, rotate it first.

What is the difference between git rm and git rm --cached?

Plain git rm stages a deletion AND deletes the file from disk. git rm --cached stages the same deletion but leaves the disk file untouched. Gone everywhere vs gone from the repo only.
