git: "fatal: tag 'v1.0' already exists" - how do I move a tag to another commit?

Short answer

Tags are meant to be immutable release markers, so git never re-points one silently. Move it explicitly: git tag -d v1.0 then git tag v1.0 (or git tag -f v1.0) - only the label moves, never the commits. If the tag was already pushed, the remote refuses too ('already exists in the remote'); publish with git push --force <remote> v1.0. Warn anyone who fetched the old tag: git fetch will not update it for them. If the tag reached users or a registry, cut a new version instead.

Common mistakes when moving a tag

  1. Assuming git push --tags fixes everything. It pushes all tags but still rejects each existing remote tag individually. Only --force (or deleting the remote tag first) moves a published tag.
  2. Forgetting teammates keep the old tag. git fetch never overwrites an existing local tag - people who fetched the old v1.0 keep it until they tag -d and re-fetch. Announce the move.
  3. Moving a tag that reached consumers. Once v1.0 is in a registry, a release page, or a user's pinned build, re-pointing makes the name mean two artifacts. Cut v1.0.1.
  4. Fearing the delete step. git tag -d removes the label file only - the commit is untouched, and the printed hash ('was 6d1bc10') recreates the tag instantly if you delete the wrong one.

Frequently asked questions

Why does git tag refuse to overwrite?

Tags are designed as immutable release markers: if v1.0 could drift silently, two people could ship different code under one version name. The move is possible but must be explicit (tag -d, or tag -f).

How do I move a tag to another commit?

git tag -d v1.0, then git tag v1.0 (on the right commit) - or git tag -f v1.0 in one step. Verify with git rev-parse v1.0 that the name resolves to the new hash.

Why does the remote reject the moved tag?

Same rule, other side: the remote will not clobber an existing tag name pointing elsewhere. git push --force <remote> v1.0 publishes the move - the '+' in the output marks the forced update.

Will my team get the moved tag on fetch?

No. git fetch never overwrites a local tag they already hold. They must git tag -d v1.0 and fetch again - so coordinate any moved tag, and never move one that reached users.

tag -f or delete-then-recreate?

Identical result: only the ref file moves. The delete version prints the old hash as a recovery anchor; -f is one step. Annotated tags (-a -m) follow the same mechanics and are preferred for real releases.
