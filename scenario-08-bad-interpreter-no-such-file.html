bad interpreter: No such file or directory. How do I fix it?

Short answer

On a script that clearly exists, this error usually means the interpreter named on its first line cannot be used. A common cause is Windows (CRLF) line endings: the first line really reads #!/bin/bash plus a hidden carriage return. Check with file script.sh and look for CRLF. Fix with dos2unix script.sh or sed -i 's/\r$//' script.sh, then run ./script.sh again. It changes only that one file.

Common mistakes with bad interpreter

  1. Adding more permissions. chmod 777 or sudo cannot help: the file's bytes are the problem, not who may run it.
  2. Deleting and retyping the script. It works, but it hides the cause. The next file you download can fail the same way.
  3. Starting it with bash cleanup.sh as the fix. That skips the first line, so it can look fixed. In this lab it printed the message with a hidden carriage return still attached, which can confuse whatever reads the output.
  4. Believing the message literally. No such file or directory is about the interpreter name with its hidden carriage return, not about cleanup.sh, which is right there.
  5. Saving Linux scripts on Windows without checking. Many editors can save with LF line endings. Check the setting before saving a script for Linux.

Frequently asked questions

Why does it say No such file or directory when the file exists?

The missing thing is the interpreter named on the script's first line. A hidden carriage return after #!/bin/bash makes Linux look for a program whose name ends with that character, which does not exist.

What does ^M mean in the error?

It is how the carriage-return character is shown. Windows text files end lines with CR and LF; Linux uses LF only. On a real terminal the hidden CR can make the error line look garbled instead.

What does exit status 126 mean here?

The script was found but could not be run. 126 can come from a missing execute permission or, as in this recording, an unusable interpreter. 127 would mean the command was not found.

How do I see the line endings of a file?

file cleanup.sh reports CRLF line terminators when they are present. cat -A cleanup.sh shows the carriage returns as ^M at the end of each line.

Is sed -i 's/\r$//' the same as dos2unix?

For this problem both remove the carriage returns. dos2unix is the dedicated tool used in this recording; sed is present on nearly every Linux system.

Could the cause be something else?

Yes. bad interpreter also appears when the first line names a program that is not installed, or a path that does not exist. This recording covers the CRLF cause only.
