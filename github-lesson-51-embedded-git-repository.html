git: "warning: adding embedded git repository" - why is my folder empty?

Short answer

The folder you added has its own .git - so git stored a gitlink (mode 160000): one entry pointing at the library's commit hash, not its files. Clones get an empty directory. To vendor the files for real: git rm --cached path, then rm -rf path/.git, then git add path and commit. If you need the library's own history and pinned upgrades, use git submodule add <url> path instead - it creates the matching .gitmodules entry that makes the gitlink fetchable. Check with git ls-files --stage: 160000 = pointer, 100644 = real file.

Common mistakes with embedded repositories

  1. Treating the warning as noise because the add succeeded. The add DID succeed - as a gitlink. The warning is the only signal you get before every clone receives an empty folder. Read the hint block; git wrote you the whole diagnosis in it.
  2. Deleting the nested .git before git rm --cached. If the gitlink is already committed, removing .git first leaves the 160000 entry in history and the index; the next add then fights a stale entry. Order matters: rm --cached the pointer, then un-repo the folder, then re-add.
  3. Fixing it on GitHub's website or by re-cloning. The empty folder is not a sync glitch - it is what the repository contains. No amount of re-cloning fills it; the fix is changing what is committed (files instead of a gitlink), then pushing.
  4. Reaching for submodules to repair a mistake. submodule add on top of an existing gitlink mess usually fails ('already exists in the index'). Clean the gitlink first (rm --cached), then decide deliberately: vendor (remove .git) or submodule (add with a URL).

Frequently asked questions

What does 'warning: adding embedded git repository' mean?

The folder you added contains its own .git - it is a separate repository. git stored a gitlink (mode 160000): a pointer to the embedded repo's current commit, not its files. The add succeeded; the content did not go in.

Why is my folder empty after cloning or on GitHub?

Your repo holds only the gitlink - a commit hash with no source URL. Without a .gitmodules entry, clones cannot fetch the content, so the directory materializes empty; GitHub renders it as a grey unclickable folder icon.

How do I fix an accidentally added embedded repository?

git rm --cached path (index only, files stay), rm -rf path/.git (folder becomes ordinary files), git add path, commit. Verify with git ls-files --stage: expect mode 100644 entries and no 160000.

Should I use a git submodule instead?

Only if you need the library's own repo: pinned upgrades, upstream URL, its tags. git submodule add <url> path creates the gitlink plus the .gitmodules entry that makes it fetchable (clone with --recurse-submodules). For a snapshot you will not upgrade, vendored files are simpler.

How do I check whether my repo contains gitlinks?

git ls-files --stage and read the mode column: 160000 = gitlink (pointer), 100644/100755 = real file. A 160000 entry with no matching path in .gitmodules is the empty-folder trap.
