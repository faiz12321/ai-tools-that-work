git revert: "error: commit ... is a merge but no -m option was given" - how do I undo a merge?

Short answer

A merge commit has two parents, and revert needs to know which side to keep - that is what -m (mainline) selects. Parent 1 is always the branch you were ON when merging, so undoing a feature merge into main is git revert -m 1 <merge-commit>. Then beware the trap: merging that branch again says Already up to date with its changes missing - git tracks ancestry, not content. The fix is git revert <revert-commit> (revert the revert), or rebuild the branch if it moved on.

Common mistakes when reverting a merge

  1. Guessing the -m number. -m 1 keeps the branch you were on; -m 2 keeps the merged-in branch. Guessing wrong keeps the wrong content and looks like a successful revert. Check %P first.
  2. Expecting git merge feature to bring the changes back. After a reverted merge, the branch is still an ancestor in history - merge says 'Already up to date' while the changes stay missing. Revert the revert, or rebuild the branch.
  3. Rewriting instead of reverting on shared branches. Resetting away a pushed merge forces everyone else to repair their clones. Revert adds one commit and keeps every clone valid.
  4. Forgetting new commits on the feature branch. Revert-the-revert restores only what the original merge brought in. If feature advanced, rebase it onto main (new hashes) and merge that.

Frequently asked questions

Why does git revert refuse on merge commits?

Revert inverts the diff between a commit and its parent. A merge has two parents, hence two diffs - git cannot guess which side you want to keep, so it asks for -m (mainline).

Which parent number do I pick?

Parent 1 is the branch you were on when merging (main when you merge a feature in); parent 2 is the branch merged in. git show --no-patch --format=%P <merge> prints them in -m order. Undoing a normal feature merge is -m 1.

Why is the branch 'Already up to date' but its changes are gone?

Merging checks ancestry: the branch tip is reachable from the old merge commit, so git considers it merged. Your revert changed content, not ancestry - merge never re-examines content. Revert the revert to re-apply the changes.

Is reverting a merge safe on main?

Yes - it is the recommended fix for a bad merge on a shared branch: one new commit, no rewritten history, valid clones everywhere. The hazard to plan for is the later re-merge, not the revert.

What if the feature branch got new commits after the bad merge?

Revert-the-revert restores only the old content. Rebase the feature branch onto current main (giving its commits new hashes) or cut a fresh branch from it, then merge - git will see new, unmerged commits and apply everything.
