git: "You have not concluded your merge (MERGE_HEAD exists)"

Short answer

A merge that stops on conflicts is not over - git parks it as a state, marked by a file called .git/MERGE_HEAD. While that file exists, starting another merge or pull is refused: fatal: You have not concluded your merge (MERGE_HEAD exists). There are exactly two exits: git commit after resolving (which creates the merge commit and concludes the state), or git merge --abort (which cancels it and restores the pre-merge state). The message is a status report, not an error to fight.

It is not broken. It is waiting.

Common mistakes mid-merge

  1. Re-running the merge to "make sure". A parked merge cannot be restarted over itself. Before resolving, you get 'Merging is not possible because you have unmerged files'; after resolving and staging, you get the famous 'MERGE_HEAD exists'. Both mean the same thing: the merge is in progress - conclude or abort, do not restart.
  2. Deleting .git/MERGE_HEAD by hand. The file marks the merge and names its second parent. Delete it and your next commit becomes an ordinary one-parent commit - the merge relationship is silently lost, and the history lies about what happened. git commit and git merge --abort both handle the file for you.
  3. Thinking 'fixed' means 'finished'. After you resolve and stage, git status says 'All conflicts fixed but you are still merging'. The resolution is a proposal; the merge commit is the signature. Nothing is concluded until git commit runs.
  4. Trying --abort after committing. --abort only works while MERGE_HEAD exists. Once the merge commit is created, the undo is git reset (unpushed) or git revert -m (shared) - a different tool for a different situation.

Frequently asked questions

What does "You have not concluded your merge (MERGE_HEAD exists)" mean?

A merge stopped on conflicts is a state, not a finished act. Git parks it with a small file, .git/MERGE_HEAD, holding the hash of the commit being merged in. While that file exists, git refuses to start a new merge or pull. It is a status report, not corruption - the merge is waiting for its final act.

How do I fix "MERGE_HEAD exists"?

Two exits. If you resolved the conflicts and staged the files (git status says "All conflicts fixed but you are still merging"), run git commit - creating the merge commit concludes the merge and MERGE_HEAD disappears. If the merge was a mistake or too big, run git merge --abort - it restores the pre-merge state and deletes MERGE_HEAD. Never delete the file by hand.

What is the difference between "unmerged files" and "MERGE_HEAD exists"?

Both block a new merge, but they describe different moments. "Merging is not possible because you have unmerged files" fires while conflicted files are still unresolved. "You have not concluded your merge (MERGE_HEAD exists)" fires after you resolved and staged them - the work is done, but the merge commit does not exist yet. The first asks you to resolve; the second asks you to commit.

Can I just delete .git/MERGE_HEAD?

You can, but you should not: the file is how git knows the merge is in progress and who the second parent of the merge commit should be. Deleting it by hand leaves a staged resolution with no merge state - the next commit becomes an ordinary one-parent commit that silently drops the merge relationship. Use git commit to conclude or git merge --abort to cancel; both handle the file correctly.

When should I use git merge --abort?

When the merge has not committed yet and you want out: wrong branch, wrong moment, or a conflict far bigger than expected. It restores everything to the pre-merge state. After the merge commit exists, MERGE_HEAD is gone and --abort has nothing to act on - undoing a committed merge is git reset (if unpushed) or git revert -m (if shared).
