How to see which line endings a text file uses

Short answer

Windows usually ends a line with two bytes, CRLF. Linux and Mac use one, LF. A file can even contain both. This lesson builds a small read-only Python tool that counts the line endings in a text file or in the text files of a folder and flags the files that mix them. The tool has no code that changes or creates a file. It reads raw bytes, because Python hides the difference when it reads text. A clean report does not mean a program will like the file.

Follow along and build it step by step. You add each file yourself, run each command, and see the real recorded result.

Common mistakes

  1. Reading the file as text and trusting it. Python turns CRLF into a plain new line when it reads text. The first version in this lesson shows an LF-looking result for a file that really has CRLF.
  2. Assuming one kind per file. A file can mix kinds, for example after pasting lines from another system. The tool counts each kind and says mixed.
  3. Treating "no line endings" as a problem. A file with one line and no ending has none to count. The tool reports that plainly.
  4. Treating a clean report as a guarantee. The tool only counts line endings in a few file types. A program can still dislike a file for other reasons.

Frequently asked questions

What are CRLF and LF?

They are two ways to mark the end of a line. CRLF is two bytes, carriage return then line feed. LF is one byte, the line feed. Python's io documentation lists the three endings it recognises: \n, \r and \r\n.

Will this change my files?

No. The tool opens files for reading in binary mode only. Tests check that file contents are not changed and nothing is created.

Why does the tool read bytes instead of text?

When Python reads text it translates line endings into a plain new line, so the difference disappears. Reading bytes keeps what is really in the file.

Why is a UTF-16 file not counted?

Text saved as UTF-16 contains zero bytes, and the tool skips any file with a zero byte. That also skips real binary files. Counting UTF-16 files is not built.

Does a clean report mean the file is fine?

No. It only means the file has no mix of line endings among the types the tool checks. Programs can have other requirements.

Why are file names printed in quotes?

Special characters are written as escapes so the report shows on any console.
