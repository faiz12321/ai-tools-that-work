git: make your repo match the remote exactly (git fetch + git reset --hard origin/main)

Short answer

The "force pull" is two commands: git fetch origin, then git reset --hard origin/main. Your branch, index and tracked files become an exact mirror of the remote. Local commits fall off the branch (reflog still knows their hashes, for a while); uncommitted changes to tracked files are gone permanently; untracked files survive untouched.

Common mistakes with reset --hard to a remote

  1. Resetting to a stale origin/main. origin/main is only as fresh as your last fetch. Reset to yesterday's picture and you mirror yesterday. The recipe is fetch first, reset second.
  2. Believing status when it says "ahead 1". Status compares against your last fetch. The remote may have moved; only git fetch refreshes the truth, after which an honest divergence reads "ahead 1, behind 1".
  3. Expecting reflog to save uncommitted work. Reflog journals commits and HEAD moves. Your unsaved edit was never committed, so no log anywhere remembers it. --hard is the point of no return for the working tree.
  4. Using it to escape a push rejection. "Push rejected" means the remote has work you lack - fetch and integrate it (lesson 2). Mirroring the remote over your colleagues' commits is how work gets silently abandoned.

Frequently asked questions

How do I force git pull to overwrite my local files?

There is no pull --force for this. The recipe is two commands: git fetch origin, then git reset --hard origin/main (substitute your branch). Fetch refreshes your picture of the remote; reset moves your branch, index and tracked working-tree files to match it exactly.

What does git reset --hard origin/main delete?

Uncommitted changes to tracked files are overwritten with no backup - they are not in any commit, so reflog cannot bring them back. Local commits leave the branch but stay in the object store for a while; git reflog shows their hashes and git switch -c rescue <hash> recovers them. Untracked files are never touched by reset.

Why does git status say "ahead 1" when the remote has actually moved on?

git status compares your branch with your last fetched copy of origin/main. Until you run git fetch, it is reporting stale news. Fetch first, then read status: a true divergence shows as "ahead 1, behind 1".

Does git reset --hard origin/main change the remote?

No. Reset is purely local: it moves your branch pointer, index and working tree. Nothing is sent to the remote. The remote only changes when you push.

Can I undo git reset --hard?

For commits, yes, for a while: git reflog lists where HEAD has been, so git switch -c rescue <old-hash> or git reset --hard <old-hash> restores the abandoned commit. For uncommitted changes, no: they were never stored anywhere, and the reset overwrote them.
