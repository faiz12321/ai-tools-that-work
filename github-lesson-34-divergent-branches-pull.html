git: "Need to specify how to reconcile divergent branches" on pull

Short answer

Both sides of the branch moved, and git will not choose between merge and rebase for you. Answer once with git pull --no-rebase (join with a merge commit) or git pull --rebase (replay your commits on top), then make it permanent with git config pull.rebase true or false - and the error never comes back.

The situation
You and a teammate both started from the same main on Monday. They pushed "add retries" this morning; you committed "add ui stylesheet" an hour later. Your git pull should simply bring their work in - instead git prints a wall of hints and stops: "fatal: Need to specify how to reconcile divergent branches."

Common mistakes with divergent pulls

  1. Reading the fatal as lost work. Nothing was undone or deleted: the fetch already happened (the new commit is local), and the join simply waits for your answer.
  2. Rebasing commits others already have. Rebase re-creates commits with new hashes; on shared or pushed commits that hands everyone else confusing duplicates. Rebase only what is still yours.
  3. Setting --global from the hint by reflex. The hint offers --global for all repos; a repo-local git config covers just this project. Pick the scope you mean.
  4. Thinking --no-rebase changed your default. One-off flags answer once. Until a pull.rebase or pull.ff config exists, the next diverged pull asks again.

Frequently asked questions

What does "fatal: Need to specify how to reconcile divergent branches" mean?

Both your branch and the remote branch moved since your last shared commit. git pull already fetched the new work; it only refuses to CHOOSE between merging and rebasing, because the two produce different history. Nothing is broken or lost.

How do I fix the divergent branches error?

Answer once: git pull --no-rebase to join with a merge commit, or git pull --rebase to replay your local commits on top of the fetched ones. Then stop being asked: git config pull.rebase true (or false) in the repo, or with --global for all repos.

For git pull, should I choose merge or rebase?

Merge (pull --no-rebase) keeps the true record: both commits stay untouched and a merge commit joins them. Rebase (pull --rebase) replays your local commits on top, giving linear history but new hashes for your commits. Teams that share the branch usually merge; solo cleanup usually rebases.

Is it safe to run git pull --rebase?

Safe when your unpushed commits are the only ones being replayed - the error case here. Rebase re-creates commits with new hashes, so never rebase commits you have already pushed or shared with others.

How do I make my choice permanent so git pull stops asking?

Run git config pull.rebase true (always rebase), git config pull.rebase false (always merge), or git config pull.ff only (only allow fast-forwards). Add --global to apply it to every repository. Verify the silent write with git config --list --show-origin | grep pull.
