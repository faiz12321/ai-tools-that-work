git push: "refusing to update checked out branch" - how do I fix it?

Short answer

The remote is a non-bare repository - someone created it with plain git init, so it has a working tree with main checked out. git refuses to move a branch anyone has checked out, because the ref would advance while that repo's index and files stay behind. The fix is not an override flag: recreate the shared repo as bare (git clone --bare old new, history intact) and push to that. Confirm with git rev-parse --is-bare-repository: false before, true after.

Do not 'fix' this by setting receive.denyCurrentBranch=ignore on someone's working repo - the push then corrupts their checkout state, the exact thing the refusal prevents. The inspection commands (rev-parse, symbolic-ref, ls-remote) are all read-only; git clone --bare creates a new directory and never modifies the original.

Common mistakes with this refusal

  1. Setting receive.denyCurrentBranch=ignore on the shared repo. The hint mentions it, so people reach for it. It makes the push succeed while desyncing the remote's index and work tree from its branch tip - the next person there sees phantom modifications and can commit a revert of your work without knowing.
  2. Trying to delete or force-update the checked-out branch. git refuses that too, for the same reason. The guard is about the checkout, not about your permissions; the fix is changing the repo's shape, not fighting the guard.
  3. Re-initializing with git init --bare IN the same directory. init --bare on top of an existing non-bare repo does not cleanly convert it. Migrate with git clone --bare (new path, full history), retire the old folder.
  4. Thinking the error means your branch or commit is wrong. Nothing about your side is wrong. 'failed to push some refs' is the generic summary; the specific cause is 'branch is currently checked out' - read the remote: lines above the summary.

Frequently asked questions

What does 'refusing to update checked out branch' mean?

The remote repo has a working tree with that exact branch checked out. Moving the ref would make its HEAD, index and files disagree, so git blocks the push by default (receive.denyCurrentBranch=refuse). Your commit is fine; the destination's shape is the problem.

How do I fix it?

Make the shared repo bare: git clone --bare /path/old /path/new (keeps all history) or git init --bare for a fresh one, push to the bare path, and point everyone's remote at it. Check with git rev-parse --is-bare-repository: it should print true.

Should I set receive.denyCurrentBranch=ignore?

Almost never - it disables the protection, not the problem, and the remote's checkout goes stale. The legitimate variant is updateInstead on a machine you control, for push-to-deploy: git then refreshes the work tree on every push (and still refuses if that tree is dirty).

What is a bare repository, exactly?

Just the .git contents - refs, objects, config - with no working tree and no checked-out branch. Bare repos cannot be edited in, which is exactly why they are safe to push to. Every hosted remote (GitHub, GitLab) is a bare repo underneath.

Can I ever push to a non-bare repo?

Yes: to any branch that is not checked out there, the push goes through normally. Cloning and fetching from a non-bare repo also always work. Only pushing to its CURRENT branch is refused.
