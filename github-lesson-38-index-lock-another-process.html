git: "Another git process seems to be running in this repository" (index.lock)

Short answer

A command that writes the index found .git/index.lock already there - a do-not-disturb flag left behind by a crashed or killed git process (or a genuinely running one). Reads like git status keep working; only writes are refused. Check that no git is actually running, then delete exactly one file: rm .git/index.lock. Never delete the whole .git folder.

Common mistakes with index.lock

  1. Deleting the lock while git is genuinely running. If another terminal is mid-rebase or an editor has git commit open, the lock is doing its job. Removing it then invites two writers into the index at once. Check first, delete second.
  2. Deleting the whole .git folder. That folder IS your repository - history, branches, stashes, everything. The fix is one zero-byte file with an exact name, never the folder.
  3. Re-cloning to escape it. Works, but abandons every unpushed commit and branch. Thirty seconds of checking plus one rm achieves the same with nothing lost.
  4. Reading it as corruption. The calm git status is the tell: reads pass, writes refuse. A stranded flag, not damaged data. Your files were never touched.

Frequently asked questions

What does "Another git process seems to be running in this repository" mean?

A command that writes the index (add, commit, merge, rebase) tried to create .git/index.lock - a do-not-disturb flag that prevents two gits writing at once - and the file was already there. Either a git process really is running (another terminal, an editor opened by git commit, an IDE), or an earlier process crashed and left the flag behind.

How do I fix "fatal: Unable to create .git/index.lock: File exists"?

First confirm no git process is actually running - check other terminals and editors, or run ps -eo comm= | grep -c '^git$'. If nothing is running, delete exactly one file: rm .git/index.lock. Reads and writes work immediately after. Never delete the whole .git folder.

Why do git status and git log work while git add fails?

The lock guards writes to the index. Read-only commands (status, log, diff) never need it, so they pass; any command that writes (add, commit, merge, rebase) is refused. That split is the signature of a stranded lock.

Is it safe to delete .git/index.lock?

Safe only after you confirm no git process is genuinely running - deleting it while a real rebase or commit is mid-write can corrupt the index. With no process running, the file is a zero-byte leftover and removing it loses nothing.

Will deleting index.lock lose my uncommitted changes?

No. The lock file contains nothing (zero bytes); it is only a flag. Your modified files, staged changes and commits are untouched. After removal, git add and git commit work normally on the changes that were there all along.
