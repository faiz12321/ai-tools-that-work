Common mistakes

  1. Reusing an old JPG name. Native conversion commands can replace an existing output. This wrapper requires a NEW output folder outside the source and uses exclusive creation for each JPEG.
  2. Expecting a fresh terminal to fix every PATH problem. Processes inherit environment from their parent. A new terminal can still have stale or wrong PATH. Verify your actual installed executable; do not paste this recording's paths.
  3. Equating a decoder check with photo preservation. The first image at index 0 is used, orientation applied, alpha flattened on white and metadata stripped. No sequence, depth, motion, HDR, dates or color fidelity promise.
  4. Retrying after a partial failure. Completed copies stay; sources are not automatically cleaned up or restored. Inspect the partial output and keep originals. A new output name does not make native decoding safe for hostile files.

Frequently asked questions

Is ImageMagick a GUI photo app?

This lesson uses its command-line executable, magick in version 7 or convert in version 6. Some builds also include graphical tools. The absence of a pinned icon does not prove installation failure.

How does the wrapper find the program?

It first checks the supplied --magick path/name or MAGICK_EXE environment value, default magick. If that default is absent, Windows checks for exactly one ImageMagick*/magick.exe under Program Files; Ubuntu can fall back to convert. It verifies the version output says ImageMagick. Multiple Windows candidates require your explicit --magick path. This is not executable authentication.

Will this preserve all my phone-photo features?

No. It intentionally makes lossy JPEG copies from index 0 only, auto-orients, flattens transparency on white and strips metadata. Extra images, HDR, Live Photo motion, depth, dates and color may be lost or changed. Keep the HEIC originals and inspect real results separately.

What does the source digest prove?

The wrapper compares every selected source filename and SHA256 digest before and after a completed batch. Tests also check source modification times. This detects those byte/inventory changes in the fixtures; it does not prevent concurrent changes or prove a backup or every metadata field.

What inputs are supported?

Only 1-100 nonrecursive HEIC files with simple ASCII stems of 1-64 letters/digits/underscores/dashes, 25MiB per file and 100MiB selected total. Case-colliding output names, other entries, links/reparse/hardlinks/special files and traversal are refused. Native decoding and Python buffering can still use memory/time.

Are these real photos?

They are real HEIC-encoded tiny images generated from fictional colored shapes, not camera photographs. The JPEG tests decode them, check expected dimensions and nonuniform pixels. They cannot validate a real phone library.
